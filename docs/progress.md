## M4 — Terms engine and pricing
- Pure calculators (`modules/pricing`): early payment (fixed table and pro-rata annual rate modes, buyer return, bank commission, warnings), financing (discount-to-yield upfront, actual/365, per-line 2 dp rounding, platform fee payer bank/supplier, premium payer), FX (`mid × (1 − spread)`, INR amounts, USD equivalents via INR crosses), calendar hook (tenor, weekday calendar; real calendars in M7). `SimFxRateProvider` with quote validity window; daily movement is opt-in (off by default so demo numbers are stable).
- **All golden numbers are named, passing tests** (`test/pricing.test.ts`): 6.14%, 12.41%, 99,000 / 200 / 800, 865.48 / 100 / 27 / 180 / 1,172.48 / 88,827.52 / 8.03%, bank-pays-fee 1,145.48 / 88,854.52 / 7.84%, 88.1348, ₹87,25,345. Loss cases A/B/C land in M8.
- Rule engine (`terms/rules.ts`): pure condition tree (in/nin/eq/neq/lt/lte/gt/gte/exists, all/any/not) with plain-language reasons (e.g. "Tenor of 135 days is above this bank's maximum of 120 days."), the BR-8 JSON verbatim, and fast-check property tests for composition (AND/OR, De Morgan, double negation, ordering).
- Terms: JSON schemas (zod, `TERMS_SCHEMA_VERSION = 1`) for platform, bank (CT-1) and insurer (CT-2) terms; sets + versions (draft → pending → active → retired); DB trigger makes active versions immutable for every role; maker-checker enforced now (submit / approve by a different user; M9 adds the studio UI and review notes); future-dated effective versions; layer resolution in the exact BR-9 order with ties by effective date, priority, version, plus a per-parameter explanation; guardrails (min dispute window, assignment notice, sanctions block, FX spread cap, small-supplier cost cap) named in the error. Seeds: platform defaults, 3 bank and 2 insurer term sets exactly per BR-6/BR-7.
- Offer evaluation (`terms/evaluate.ts`, `POST /invoices/:id/eligibility`): gates 5–7, plain reasons, quote with net cash, all-in cost, INR amount at the bank's rate, terms version ids, saving vs. the supplier's borrowing rate. Small suppliers' advance is **capped at the insured cover** (BR-11.6) and the cap is reported (deviation from "block": clamping keeps the offer useful).
- Simulator: `POST /terms/simulate` runs a draft bank body against 20 deterministic sample invoices and diffs against the active terms.
- Tests: 65 new (132 total). Decision recorded: premium = rate × insured amount × number of started 90-day periods (matches the 180.00 golden for a 60-day tenor).

## M5 — Insurance and cover
- Migration 006: `insurance.buyer_limits` (reserved/used columns, check constraint so exposure never exceeds the limit) and `insurance.cover_records` (one per invoice; requested / approved / partial / declined / expired / uninsured; SLA, validity, gateway, reservation and consumption). RLS: insurer, supplier, buyer and platform can read; only the insurer or platform can update. Relationships carry an `insurer_org_id`.
- Accepting an invoice raises a cover request through the outbox (`invoice.accepted` handler in the new worker). No insurer on the relationship means `uninsured`: financing is unavailable but early payment stays open. SLA is 24 h; the cover record shows when it is overdue.
- Underwriter decision: approve at the term-set percentage (by buyer tier), approve lower (status `partial`), or decline with a reason. Approval reserves the insured USD amount against the buyer limit with a conditional UPDATE, so parallel approvals can never over-consume (tested with five concurrent approvals); if headroom is short the cover is reduced and the reason says so. Limits cannot exceed the insurer's own policy caps or fall below current exposure. Consume on funding and release on cancel are ready for M6/M7; unused cover expires after 30 days and frees the limit.
- Gateways (XB-5): manual workflow (default), simulated insurer API polled by the worker (deterministic 1–3 h delay, request/response logged for the integration inspector), and a CSV file exchange (export open requests, import decisions with per-row errors).
- `POST /invoices/:id/eligibility` now reads the real cover record: a declined, pending or uninsured invoice reports why, a partial cover below the bank's minimum is refused, and a small supplier's advance is capped at the insured percentage.
- Worker (`src/worker.ts`): outbox drain, acceptance reminders, insurer API, cover expiry, terms expiry; started by the server on an interval and by `env.work()` in tests. Outbox handling hardened: per-event savepoint, `last_error`, parked after five attempts so a poison event cannot block the queue. DB pool now ignores idle-client errors.
- Web: cover request queue with decision form (INS-02), buyer limits (INS-03), cover panel on the invoice detail page, navigation for insurers.
- Tests: 16 new (148 total).

## M6 — Marketplace, liens, early payment
- Migration 007: invitations, offers, financing requests, liens + lien events, assignment notices, discount schedules, early payments. RLS: a bank reads an invoice, its documents, acceptance, history and cover record **only if invited** (policies reference `marketplace.invitations`, which references nothing else, so there is no recursion). Tested through the API and directly against the database as the bank role. Drafted offers are invisible to the supplier; the buyer never sees bank rates.
- Funding gates (BR-1 1–4) as an ordered list with plain reasons; failing any parks the invoice as `NotEligible` and a re-check is allowed. Opening invites the supplier's and buyer's preferred banks plus the partner bank; white-label mode (`EARLIO_MODE=white-label`) invites only the partner. Gates 5–7 run per bank through the shared `quoteForBank` (also used by `/invoices/:id/eligibility`).
- Offers: a bank composes within its terms (advance cannot exceed terms, rate 0–60 %, FX spread and small-supplier cost cap enforced by the platform guardrails), previews the price, and sends. States Drafted → Submitted → Selected / Rejected / Expired / Withdrawn / Superseded. Sending re-prices with current terms and cover. Expiry is a worker job; an invoice with no live offers returns to OpenForFunding. API offers use an `Idempotency-Key` header (unique per bank). Deviation: no HMAC request signing in the MVP; API offers authenticate with the normal session.
- Comparison read model: bank offers cheapest first (all-in %, net cash, INR, FX rate, cover %, "insured, non-recourse", saving against the supplier's borrowing rate, expandable cost breakdown) plus the early-payment option at today's date.
- Financing request: select (reserves bank limits for buyer and supplier, creates the Reserved lien, locks the route) → supplier consent (Approver; plain-language consent text, assignment notice with governing law, US filing stub, Singapore data-consent flag) → bank confirm (re-checks sanctions/KYC, dispute window, cover vs. the bank's minimum, buyer's assignment acknowledgement) → `completeFunding` (lien Active, limits and cover consumed, competing offers rejected, invoice Funded, route financing). Cooling-off cancel and bank decline release everything and restore the offer. Deviation: the lien is Reserved at selection rather than at bank confirmation, which is what makes parallel selects safe. The M6 bank confirm instructs and credits the payment in one step; M7 replaces it with the disbursement machine and calls `completeFunding` on credit.
- Lien conflict: two parallel selects on one invoice give exactly one winner (tested); the loser gets 409 `lien_conflict` and the conflict is written to the audit log and lien history in its own transaction so it survives the rollback.
- Early payment: supplier publishes a schedule (dates with discounts, or an annual rate applied pro rata) with warnings against its borrowing rate; buyer quotes and confirms with cash or a bank loan. The BR-2 example reproduces exactly (99,000 / 6.14 % / commission 200 / saving 800), cash funding earns no commission. Confirming marks the invoice Funded with route `early_payment`, withdraws every other offer and locks the route; confirming is blocked until the dispute window ends.
- Web: funding panel on the invoice detail page for the supplier (request funding with gates, comparison, choose, consent, cancel, discount schedule), the buyer (assignment notice acknowledgement, early-payment calculator and confirmation) and the bank (offer composer with price preview, financing confirmation); bank invitations inbox; admin lien registry.
- Tests: 24 new (172 total).

## M7 — Settlement, reconciliation, notifications, control room
- Migration 008: collection accounts, disbursements and their event trail, expectations (one payment reference per invoice), bank transactions (unique per bank, source and bank id), ledger entries, exceptions, webhook nonces, notifications, and the simulated bank feed.
- **Disbursement (ST-1).** `financing.approved` (bank confirm) instructs the payout: FX booked at the bank's rate (88.1348 for the golden case, ₹78,31,175.35), value date from the bank's cut-off time and the India/US/Singapore holiday calendars (seeded, flagged VERIFY), queued if it falls later than the bank's local date, sent by the worker, credited one hour later by the simulated bank. Only the credit completes funding (lien active, limits and cover consumed, invoice Funded), so Funded now means the supplier has the money. Rejections retry up to three times, then the payment is reversed, the financing fails, locks are released and a `DisbursementFailed` exception is raised. Mismatched credits and returned funds raise exceptions operations can accept. Fault injection is a platform setting (none, reject, timeout, mismatch, return, seeded random).
- **Collection (ST-2 to ST-4).** On `financing.funded` the buyer is issued `EARL-<invoice>-<check>` and the bank's collection account. Payments arrive by HMAC-signed webhook (timestamp window, nonce replay protection, per-bank secret derived from the master key) or as statement lines pulled from the simulated feed; the same bank transaction is never booked twice and a statement line that echoes a callback is linked rather than double-counted. Matching is by reference and amount: exact payments are distributed (principal to the bank, retention released to the supplier in INR at the settlement FX rate, platform fee noted), the lien and limits are released and the invoice is Settled; the next statement pass reconciles it to Closed with no manual step. Short, over, late, unmatched and wrong-currency payments become exceptions with allowed actions (assign to invoice, wait, accept as full, refund, acknowledge). A funded invoice past due becomes Overdue.
- Early-payment route: a worker books the ledger lines and closes the invoice.
- **Notifications (CR-1).** A `*` outbox subscriber writes one row per recipient organisation and channel from English templates (a `lang` column is ready for Hindi in M10): in-app, email, and SMS/WhatsApp for key supplier and buyer events; a delivery job hands queued rows to the simulated channels and logs them in the integration inspector. Unread count, mark read, mark all read; tenants see only their own.
- **Control room (dev, demo and test only).** Virtual clock moves, fault settings, a payer simulator that produces a signed callback and/or a statement line, holiday calendars, integration-message inspector.
- Web: buyer payments due, bank/platform settlement console (exceptions with resolve actions, expectations, transactions, disbursements), payment and ledger panel on the invoice page, notification bell and centre, control room, integration inspector.
- Tests: 13 new settlement tests (185 total): golden payout, cut-off queueing, retries and reversal, mismatch resolution, end-to-end Funded → Settled → Closed with zero open exceptions, statement-only reconciliation, short pay, unmatched, late, webhook replay/bad signature/stale timestamp, notifications and tenancy, control-room permissions. The M6 funding test now drives the async path.
- Deviations: the platform fee is shown as a note line (the bank pays it under its own terms, nothing is collected by the platform); webhook secrets are derived from `WEBHOOK_KEY` rather than stored; Playwright browser E2E is not run in this unattended environment, the API-level journeys above stand in for it.

## M8 — Exceptions: disputes, credit notes, overdue and default, claims, recourse, export proceeds
- Migration 009: dispute phase/timers/decision columns, dispute messages, credit notes, defaults, dunning events, claims, recoveries, recourse and instalments, export proceeds; new `recovery` schema.
- **Pure rules** (`recovery/waterfall.ts`, 14 tests): payout waterfall (bank principal and charges first, supplier retention next), recovery sharing by largest remainder, late interest (financing rate + 2 points, actual/365), 20% recourse offset cap, three-instalment plan, credit-note effect.
- **Disputes** (SH-05/ADM-04): pre- and post-funding. A dispute freezes the invoice, late interest and dunning. Response 48 h, escalation to Earlio 72 h, time-out 240 h (platform setting, editable). Case thread with evidence; platform decides for the buyer or supplier with a cause. Supplier causes (non-delivery, quality, wrong documents, misrepresentation) on a financed invoice create recourse.
- **Credit notes** reduce the invoice. Before funding offers on the old amount are withdrawn; after funding the advance is cut pro rata, insurer cover is rescaled and the supplier owes the difference.
- **Overdue and default**: dunning at days 1, 7 and 30; the waiting period (90 days for ExportShield, waived on insolvency) and late interest are computed live and exclude frozen days; the claim window is 60 days after the waiting period and lapses if missed.
- **Claims**: the bank files with documents; the insurer reviews against exclusions (open dispute, documentation defect, shipment before limit, sanctions breach), approves, part-approves or rejects, and records the payout, which flows through the waterfall. Later recoveries are shared pro rata to losses. Golden cases A, B and C are tested.
- **Recourse** (SUP-09): a small supplier chooses automatic offset (capped at 20% of each future retention release) or a 90-day, three-instalment plan; the bank records repayments.
- **Export proceeds** (SUP-08): 9-month realisation clock per export invoice, overdue flag by the worker, bank AD reports realisation.
- Worker: dispute timers, instalment reminders, proceeds overdue, default processing; notification templates for all new events.
- Web: disputes list and case page with decision form and timer editor, dispute/credit-note forms on the invoice page (replacing the browser prompt), overdue and defaults, claims desk and recovery workbench, recourse view, export proceeds tracker.
- Tests: 28 new (213 total).
- Deviations: recourse offsets apply only to retention releases in the same currency; a claim rejection creates recourse only if none exists; late interest is booked from any payment above the amount due; a broken export-proceeds chain is flagged for the financing route rather than blocked; Playwright E2E remains infeasible here.

## M9 — Terms studio, maker-checker, white-label, admin console
- Built on the M4 engine (versions, layers, guardrails, immutability trigger). New module `src/modules/governance`, migration 010.
- **Maker-checker (CT-6).** Approving was already blocked for the person who drafted or submitted; now platform staff can no longer publish a bank's or insurer's terms (they decide their own), a checker can **send back** a pending version with a reason (the maker can also withdraw), and `GET /approvals` is the inbox: every pending version and platform-setting change with a structural diff against what is in force, who prepared it, and whether *you* may approve it (with the reason if not). The publish audit event now stores the previous and new body, so the trail carries before/after.
- **Terms studio.** Form editor for bank, insurer and platform terms (with per-field “override” ticks for scoped overrides), JSON editor with live validation and the JSON Schema, a visual AND/OR/NOT **eligibility rule builder**, **templates** (bank: standard/conservative/growth; insurer: standard/cautious), **plain-language preview** of what suppliers and buyers will see (`POST /terms/preview`), versions list with load/diff/export/submit/withdraw, and JSON **export/import** (`earlio-terms` envelope with owner type and schema version; an import becomes a normal draft and is validated like one). Overrides per buyer, supplier or corridor use the same editor.
- **Simulator (CT-9)** now covers bank and insurer drafts: 20 sample invoices, in-force vs draft eligibility, net cash and delta. Insurer drafts run through the partner bank's terms.
- **Custom requirements (CT-10).** Terms can carry `customFields` (text, number, date, select; required or not; for the financing request or a claim) and, for banks, `requiredDocuments`. They are enforced and rendered where they matter: the supplier's consent form lists missing papers (with an upload) and the bank's questions; consent is refused with a plain message until they are satisfied and the answers are stored on the financing request, where the bank sees them. The claim form shows the insurer's document list and extra questions, stored on the claim. To make this usable, suppliers may now add supporting papers (packing list, shipping bill, transport document) after acceptance and before funding; the invoice and delivery proof the buyer accepted stay locked.
- **Platform settings (ADM-07).** Dispute timers, dunning days, export realisation period, recourse causes, dispute window, governing-law text and the operating mode are *governed settings*: one platform administrator proposes (`PUT /admin/settings/:key`, 202), a different one decides in the approvals inbox; invalid values (and a dispute window under the 24-hour guardrail) are refused at proposal. The immediate `PUT /admin/dispute-timers` was removed. Fees, benchmark and free tier are platform terms and use the same version flow. The console also lists the hard guardrails (read-only: they are code) and lets the platform point a hostname at a bank. A second seeded platform administrator (`admin2@earlio.demo`) makes maker-checker demonstrable.
- **White-label (WL-1).** `GET /branding` (public) resolves the request host (or `?host=`) to a bank: display name, colours, logo (PNG/JPEG/SVG data URL or https link, 200 KB cap), welcome text. Seeded hosts: bank1/bank2/bank3.localtest.me. The SPA applies the colours as CSS variables and shows name/logo/welcome on the sign-in page and header. A bank administrator edits its own branding (low-contrast primary colours are rejected: WCAG 4.5:1 against white text); only the platform can set a hostname. The network/white-label **mode** is a governed setting; in white-label mode an unknown host gets the partner bank's branding and only the partner is invited. Bank console shows branding with live preview, the bank's own fee/price/limits summary and links to the studio and exposure limits.
- Verified: a funded invoice keeps the terms version ids it was priced on after a new version is published, and a new invoice is priced on the new one (integration test).
- Tests: 21 new (234 total, after changing the exception tests to propose-and-approve the dispute timers).
- Deviations: the white-label mode does not yet restrict *login* to the partner bank's customers (hostnames brand the experience; access control is unchanged); logos are stored inline in the organisation row rather than in object storage; the studio's override picker uses the counterparty directory, which insurers cannot call (insurers can scope by corridor only).
