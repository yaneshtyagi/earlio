## 8.1 Security controls in the application

| Area | Control | Where |
| --- | --- | --- |
| Authentication | Password (salted scrypt hash, `kernel/password.ts`) + mandatory TOTP MFA; recovery codes | `modules/identity` |
| Brute force | 10 login attempts/min per address; 5 failures lock the account for 15 min | `identity/routes.ts` |
| Sessions | Random token in `earlio_sid` cookie (`HttpOnly`, `SameSite=Lax`, `Secure` in production), only its hash is stored; 8-hour lifetime | `identity/routes.ts`, `app.ts` |
| CSRF | `x-csrf-token` header required on every mutating cookie-session request | `http/context.ts` |
| Authorisation | Role → permission matrix; org-type checks; platform cross-tenant access only through `platformCtx` and audited | `identity/permissions.ts`, `http/context.ts` |
| Tenant isolation | PostgreSQL RLS on every tenant table; the app role cannot bypass it | migrations, `db/pool.ts` |
| Machine API | API key (hash stored) + HMAC-SHA256 signature, 5-minute timestamp window, single-use nonce | `modules/integration` |
| Webhooks out (to banks) | Signed (HMAC over timestamp, nonce, body) with the bank's newest active API-key signing secret; HTTPS and public addresses only in production; 5 s timeout | `modules/integration/service.ts` |
| Bank callbacks in | `POST /api/v1/webhooks/bank/:bankId` verified with a per-bank secret derived from `WEBHOOK_KEY`, 5-minute window, single-use nonce | `modules/settlement/routes.ts` |
| Files | 10 MB cap; antivirus adapter; inline preview only for types verified from the bytes (PDF, images, text), with `nosniff` | `platform/files.ts` |
| CSV | Spreadsheet-formula neutralisation on export | `integration/csv.ts` |
| Headers | `nosniff`, `X-Frame-Options: DENY`, CSP `default-src 'none'`, `no-referrer`, `no-store`, permissions policy, CORP; HSTS in production | `app.ts` |
| Rate limiting | 600 req/min per address globally | `app.ts` |
| Audit | Hash-chained, append-only at the privilege level; verification and anchoring | `platform/audit.ts` |
| Logs | Cookie and Authorization headers redacted | `app.ts` |
| Production guards | Refuses to start with a missing/weak/default `WEBHOOK_KEY`; dev routes and demo seed are off; real clock | `kernel/secrets.ts`, `bootstrap.ts` |

## 8.2 Secrets

| Secret | Used for | Format | Who needs it |
| --- | --- | --- | --- |
| `DATABASE_URL` password | App role connection | ≥ 24 random chars | API |
| `MIGRATE_DATABASE_URL` password | Owner connection (migrations) | ≥ 24 random chars | API at start; release job |
| `WEBHOOK_KEY` | Derives each bank's secret for inbound payment-status callbacks | ≥ 24 chars, not the dev default | API; each bank's payment system holds its derived secret |
| `METRICS_TOKEN` | Protects `/metrics` | ≥ 24 random chars | API, Prometheus |
| TLS private keys | HTTPS | — | Proxy/CDN |
| Bank API keys and signing secrets | Machine API | Generated by the platform, shown once | The bank only (Earlio stores a hash) |
| User TOTP secrets, recovery codes | MFA | Stored in the database | — |

Rules:
- Keep secrets in a secrets manager and inject them as environment variables at start; never commit them, never put them in a `.env` file inside an image.
- To read secrets directly from a vault, implement `SecretProvider` (`src/kernel/secrets.ts`) and use it in `loadConfig()`; callers do not change.
- Demo credentials (`Earlio!Demo1`, `earlio_app/earlio_app`, `earlio-dev-webhook-key`) exist only for development and CI.

## 8.3 Rotation

| Secret | Procedure | Downtime |
| --- | --- | --- |
| `METRICS_TOKEN` | Update the secret → restart API → update Prometheus credentials | Scrape gap only |
| App DB password | `ALTER ROLE earlio_app PASSWORD '<new>'` → update `DATABASE_URL` → restart API. Existing connections keep working until the restart. | Restart |
| Owner DB password | `ALTER ROLE <owner> PASSWORD '<new>'` → update `MIGRATE_DATABASE_URL` → restart | Restart |
| `WEBHOOK_KEY` | Every bank's derived callback secret changes with it, so callbacks signed with the old secret are rejected (`401`) after the restart. Agree a cut-over time with the banks, update the secret, restart, and hand each bank its new derived secret through a secure channel. There is no console screen for this yet. | Coordinated |
| Outbound webhook signing | Uses the bank's API-key signing secret: rotating the bank's API key (above) changes it. During the 24-hour grace the **newest active** key signs, so the bank must accept the new secret as soon as it rotates. | None |
| Bank API key | The bank administrator uses **Rotate** in the bank console: a new key is issued and the old one keeps working for 24 hours. **Revoke** stops a key immediately. | None |
| TLS certificates | Renew before expiry (automate with ACME) | None |
| User password | No self-service reset yet (gap G9) — see [support runbook R12](../support/03-runbooks.md) | — |

After any suspected compromise, rotate immediately and treat it as a security incident (§ 8.6).

## 8.4 Production hardening checklist

- [ ] `EARLIO_ENV=production`; `GET /api/v1/system/config` shows `"simulated":false`.
- [ ] `/api/v1/dev/totp`, `/api/v1/admin/clock`, `/api/v1/sim/pay` return 404.
- [ ] `WEBHOOK_KEY`, `METRICS_TOKEN` strong and from the secrets manager; no `.env` file in the image.
- [ ] `earlio_app` pre-created with a strong password; not superuser, no `BYPASSRLS`, owns nothing.
- [ ] Database: TLS required, encryption at rest (customer-managed keys where available), not publicly reachable, PITR on.
- [ ] Object store volume encrypted and backed up.
- [ ] Only the proxy can reach the API port; `/metrics` not exposed publicly.
- [ ] TLS 1.2+ only; HSTS; wildcard certificate for tenant subdomains.
- [ ] `CORS_ORIGINS` lists only your web origins.
- [ ] All platform administrators enrolled in MFA and recovery codes stored safely.
- [ ] `security` workflow green (npm audit, CodeQL).
- [ ] Alerts in [chapter 7](07-operations-and-observability.md#74-alerts) wired and tested.
- [ ] Legal items marked *needs counsel* in [`pilot-readiness.md`](../pilot-readiness.md) signed off.

## 8.5 Access to production

- Use named, individual accounts; no shared logins to the database or servers.
- Read-only database access for support uses a separate role (e.g. `earlio_support`) with `select` only on the tables they need. Grant it `BYPASSRLS` **only** if it is audited outside the application, or have support set `app.is_platform` explicitly in each session so access is deliberate.
- Changes to production data go through the application. Where a manual fix is unavoidable, it is a reviewed script, run by two people, that writes an audit event explaining the change.
- Platform staff access to tenant data in the UI is already audited (`platform.cross_tenant_read` events).

## 8.6 Security incidents

1. **Declare** an incident, name a lead, open a channel ([support severity model](../support/01-support-model.md)).
2. **Contain**: revoke affected bank API keys; clear a bank's hostname/tenant to take its portal offline; lock affected users (set `locked_until` far in the future); to freeze all background money movement, stop the API (the worker runs inside it) and serve a maintenance page.
3. **Preserve evidence**: export the relevant `audit.events` rows and verify the chain; keep logs by correlation id; snapshot the database.
4. **Notify** affected parties and regulators as the law requires (*needs counsel* — duties differ for India, US and Singapore).
5. **Recover**: rotate secrets (§ 8.3), patch, redeploy.
6. **Review** within 5 working days; track actions to closure.
