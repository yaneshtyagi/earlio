# Earlio — instructions for coding agents

Earlio is a tri-party receivables financing platform (supplier, buyer, bank, insurer, platform admin). Read before coding:
`docs/PRD.pdf`, `docs/earlio-mvp-implementation-plan.md` (milestones M0–M10, golden numbers), `docs/progress.md`, `docs/adr/`.

## Stack (see ADR-000)
- **Backend** `apps/api`: Node 22, TypeScript, Fastify 5, Zod 4 (validation + OpenAPI), `pg` (plain SQL), PostgreSQL (migrations in `apps/api/migrations`).
- **Frontend** `apps/web`: Vite, React 19, TypeScript, TanStack Query, React Router. Talks to the API **only** through the typed client generated from `docs/openapi.json`.
- **Contract** `docs/openapi.json` is generated by `npm run openapi`; the web types by `npm run gen:client -w @earlio/web`. CI fails if they are stale.

## Commands
- `npm install` (root, workspaces)
- `npm run dev:api` — starts the API on :4000. With no `DATABASE_URL` in development it starts an embedded Postgres (data in `.pgdata`, or `EARLIO_PGDATA`), migrates and seeds the demo cast.
- `npm run dev:web` — Vite on :5173, proxying `/api` to the API.
- `npm test` — API tests (real Postgres started by `test/global-setup.ts`; no Docker needed). `npm test -w @earlio/web` for web unit tests.
- `npm run typecheck`, `npm run openapi`, `npm run gen:client`.
- Demo logins: any `<role>@<slug>.demo` (e.g. `admin@shree.demo`, `approver@northwind.demo`, `credit@aurelia.demo`), password `Earlio!Demo1`; the dev-only `GET /api/v1/dev/totp?email=` returns the current MFA code.
- Running as root (containers): Postgres cannot run as root; the launcher uses `runuser -u pgrun` (create user `pgrun`, make the repo readable by it).

## Architecture rules (non-negotiable)
1. **Modular monolith.** `apps/api/src/modules/<name>` owns its schema (`identity`, `compliance`, `invoicing`, `terms`, `insurance`, `marketplace`, `settlement`, `notify`). Modules call each other through exported service functions and the outbox, never by reaching into another module's tables for writes.
2. **Rules are data.** Bank and insurer terms are JSON validated by schema and interpreted by the rule engine. No per-bank code.
3. **Explicit state machines.** Each aggregate has a transition table; illegal transitions throw `DomainError`; each transition writes an audit event and an outbox event.
4. **Time comes from `Clock`** (`svc.clock.now()`). Never `Date.now()`/`new Date()` in domain code. The virtual clock exists only in development/demo/test.
5. **Money is `Decimal`** (`kernel/money.ts`), stored as `numeric`, passed as strings. Round half away from zero at 2 dp **per charge line**, then sum. Day count actual/365.
6. **Tenant safety.** Every tenant table has RLS keyed on `app.org_id()`/`app.is_platform()`; every request runs inside `db.tx(ctx, …)` which sets them. Platform (cross-tenant) access goes through `platformCtx(req)` and is audited. Each milestone adds isolation tests at API and raw-SQL level.
7. **Idempotent money commands** (idempotency key, stored result). Concurrency-sensitive invariants (liens, limits, audit chain) are enforced in the database and covered by parallel tests.
8. **Plain-language reasons** for every rejection (`DomainError` message is user-facing).
9. **Offers always show** annualised cost, net cash and FX rate.
10. **Integrations sit behind adapters** (`svc.adapters`); only `Sim*` implementations ship in the MVP.
11. **No secrets in code.** Demo credentials exist only in the dev seed.

## Testing
Unit tests for pure domain logic (rule engine, pricing), integration tests against real Postgres, security tests (RLS, permission matrix, CSRF, MFA), concurrency tests. Golden numbers in the plan (section 2) are named tests and must pass exactly. A milestone is done only when `npm test`, `npm run typecheck`, and the web build are green and `docs/progress.md` is updated (including deviations).
